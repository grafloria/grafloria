Tile first: the design, checked line by line against the code

The plan was "a container is a tile first, zones on top, one gesture, one commit". Three readers went through the engine, the grid binder, the split binder and the container mounting before anything gets built. The model holds. Six of my assumptions did not, and the size I gave you was wrong.

The model
Holds. A group is already an engine tile; the lock and a parallel command class are the only things that make it different.
Assumptions that failed
Six, all listed below with the line that contradicts them. Two are behaviour changes you decide; four are engineering the plan must include.
Engine work
Four small additions, each unit-tested in the engine's own spec, none of which exists today.
Size
Two to three weeks, not three to four days. The split binder is further behind than I assumed and the gesture machinery is four machines, not two.

2. The design, corrected

Engine additions

All four live in grid-pack-engine.ts and are proven in its spec the way the house does it: with a mutation the test must catch. None changes existing behaviour when unused.

D1, decided and then withdrawn by the lab. Groups were unlocked outright first (gravity and pushes like any widget). The unit suite passed; the lab failed seven long-path scenarios with one cause: a widget or a page approaching a group from above overlapped it before the hand reached it, the group was pushed away from under the hand, the hand found free space, and the group fled — its "into" zone was never reachable. Your approved loop never had that ("Outside: the container is still"). So a container is a solid tile in the engine: never pushed by a passing tile and never packed, which keeps the board still under the hand, but moved by intent — place-beside, a moved section, a dock, or a widget it refused (they pass pushSolid). The engine flag, not the binder, carries the rule.

The resolve: one recursive function over the membership tree

resolve(board, pointer, ghost, prev):
  for C in board.childContainers:                # from the model, in membership order
    if not C.frame.contains(pointer): continue
    if C.static or depth(C) + ghost.depth > POLICY.depth or C in ghost.subtree:
      return beside_or_plain(board, C, pointer)  # opaque: never enter
    z = C.zones(pointer, prev)                   # by layout: strip / band / middle; sticky at the borders
    if z is STRIP:  return { kind: 'strip',  container: C, index }
    if z is BESIDE: return { kind: 'beside', on: board, neighbour: C, side, row: board.rowAt(pointer) }
    return resolve(C.innerBoard, pointer, ghost, prev)   # tabs: the active page; grid: itself; split: the pane under the pointer
  return { kind: 'plain', on: board, cell: board.cellAt(pointer - ghost.grab) }

Coordinate spaces stay as they are today and for the same reasons: the root's dock bands are measured on the screen, container bands in world space against a frame anchored while the pointer is inside it. Stickiness is the band plus a margin for the zone the pointer already holds, applied at every container border, so a hand resting on a nested edge never bounces between levels.

The split binder implements the same peer interface for real: adopt inserts a leaf under the pointer, escalation forwards to the split's own parent, the tab-drop hooks are accepted, and the band constant is shared. The grid and split binders then differ only in their engine and their zone map.

Growth, per level, per mode

When a handler needs rows a board does not have, it calls one function, ensure rows, which asks the board's container to take that many rows from its parent. Each level answers with its own flags: escalate means take them and push the neighbours; fit means re-fit if the frame allows and otherwise refuse, and a refusal turns the into zone into a tinted refusal while the ghost stays with the parent's placement. A split level forwards the request to its parent. Every accepted row is recorded in the scope, so Escape gives it back and the batch commits it. The resize ratchet keeps its own oscillation rule; only its parent call is shared.

D2, yours: a widget that does not fit inside a fit section today slides in beside it through the nearest-cell fallback. Tile first pushes the section down instead. D3: beside lands at the pointer's row, not the container's top row. D4: a grow container takes rows when it adopts a widget; today a full page squeezes its rows instead. Fit keeps squeezing.

3. Steps, each shipped green

Step 4, first cut, shipped 2026-09-11 as element 0.4.53. Step 4 ships in two cuts. 4a is the commit and the leg: commit.ts holds the two command classes and one tileCommands that turns a board's deltas into node and group commands alike — the six hand-built group-cell sites are gone and the cross-board drop no longer drops the target board's pushed sections; the adoption leg carries beside and push, so a widget from a section or a page lands beside a container on another board and a refusing section on another board is pushed there (D2 through the leg); the palette drag runs the tile's own move path through the zone resolve and onDropIn names the board it dropped into; a dropped tile waits in the engine for the member the host adds and yields to it. 4b is the machine: drag.ts and handlers.ts over a gesture scope (tile, palette, slab and tear-out as one gesture with four sources; a group crossing boards), and project/chrome out of the binder file. Kit 856, lab 104 (L96 palette into a page, L97 beside through the leg, L98 D2 through the leg), gates green.
Steps 2 and 3 shipped 2026-09-11 as element 0.4.50, 0.4.51 and 0.4.52 (engine 0.3.9). Step 2: the recursive resolve for tile drags, then the tab drops of both binders on the same module. Step 3: solid containers, place-beside at the hand's row, a refused adoption pushing the section, every lock toggle gone. The design's D1 changed on the way, above.
Step 1 shipped 2026-09-11 as engine 0.3.8 (with element 0.4.49, which requires it): result reasons, the full gesture snapshot, setBound, placeBeside, plus one rule found on the way — a tile the kit moves on purpose forgets the cell it was pushed from, or the teleport-home memory pulls a shifted panel back under the widget. Engine spec 85, kit 814, lab 101, gates green. Decisions D1 to D4 taken as recommended.
  1. Engine 0.3.8. Result reasons, the full gesture snapshot, setBound, placeBeside. Spec additions after the push block and the maxRows block, mutation-proven. No kit change ships with it, so the kit's 813 tests and the lab prove nothing moved.
  2. zones.ts. The resolve replaces the four zone computations behind the existing behaviour. The tab, beside, adoption and tear-out specs and lab scenarios L72, L73, L79, L80, L85, L90 and L94 are the guard. A three-level fixture is added here, with the depth and cycle tests.
  3. Unlock. Groups enter the engine with the user's lock only; beside goes through placeBeside; the fifteen lock toggles and the unlock lists are deleted. D1 to D3 land here. The frame sampler from L94 becomes a shared lab assertion on every push and shift scenario.
  4. drag.ts, scope.ts, commit.ts — in two cuts: 4a commit + leg (shipped, 0.4.53), 4b the one machine. The five entry routes become one gesture; the scope spans N engines; the commit unites nodes and groups and stops dropping the target board's group displacements. Property tests over random nestings up to depth three: one engine holds the ghost, no overlaps at any level, cancel restores every snapshot, commit then undo returns to it, no tile moves twice per pointer move.
  5. Growth and parity. Ensure rows on adoption (D4), static refuses adoption, and the split binder's peer parity. The nested mode matrix runs here: grid, tabs and split crossed with escalate on and off at two levels, plus static.
  6. The file split happens inside steps 2 to 5, not after: each new module is born as its old code is deleted, so grid-binder.ts ends the work as a thin binder rather than being cut up at the end.

4. Size

Engine, two days. Resolve, two. Unlock and beside, two. The unified gesture with the scope and the commit, four to five: it touches about fifteen hundred lines and is where the four machines die. Growth, static and split parity, three. Nesting tests, the mode matrix and the lab, three. Twelve to seventeen working days with the gates run at every step, which is two to three weeks, not the three to four days I said first. Each step is releasable on its own and each step deletes more than it adds.
