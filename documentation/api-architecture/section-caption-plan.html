Section captions

Shipped in element 0.4.22 (2026-09-08): every option in "The option" below except collapsible / collapsed, with renderCaption, onCaptionAction, setCaption / getCaption, persistence through toJSON() and fromDocument. Gated by 21 unit tests (dashboard.caption.spec.ts) and kit-lab scenarios L40–L48, each frame looked at. One limit for now: a section whose parent board is in split layout has no slab overlay yet, so no caption there — that comes with the tab container, whose strip is the same band. One class bug found on the way: the parent's project() never re-synced section overlays after a frame write, so two-level sections kept bind-time chrome; fixed.

A section (a container widget) paints nothing today: no header, no label, no border. This plan gives it an opt-in caption painted by the kit, on the overlay the kit already owns, with reserved space, selection and theming, so a designer never has to draw one over the kit's frame again.

Why the kit and not the app

Three things only the kit can do for a section header. It can route the press: the kit owns the slab overlay, the ring, the handle and the hand-off between a nested board and its parent, and a header drawn outside that routing steals presses or loses them (Quantia's label tab selected the widget under it). It can reserve the pixels: a header needs room inside the slab that no child may take, and an app's header either overlaps the first child or is drawn outside the frame (the 7 px panel overlap). And it can persist it: the caption belongs in toJSON() next to layout, tree and sizing. Widget cards already follow this pattern, a default painter with renderWidget as the escape hatch; sections get the same.

The option

// DashboardWidgetSpec — containers only
caption?: false | true | string | {
  text?: string;                          // default: the container's title
  subtitle?: string;                      // muted second line (band grows to 44 px) or suffix
  description?: string;                   // an ⓘ at the end; tooltip + accessible description
  icon?: string;                          // a glyph before the text (emoji or data: URI); anything richer → renderCaption
  position?: 'inside' | 'tab';            // default 'inside'
  align?: 'start' | 'center' | 'end';     // horizontal — default 'start' (mirrored on RTL)
  valign?: 'top' | 'center' | 'bottom';   // vertical, within the band — default 'center'
  height?: number;                        // px, 'inside' only — default 28 (44 with a subtitle)
  font?: { size?: number; weight?: number | string; family?: string; color?: string; transform?: 'none' | 'uppercase' };
                                          // typography of the text; the subtitle follows at 0.85× and muted
  padding?: number | [number, number];    // inside the band: px, or [vertical, horizontal] — default [0, 10]
  margin?: number | [number, number];     // between the band and the section's content / frame — default [0, 0]
  background?: string;                    // band fill; border?: string (its bottom rule) — default from the theme
  show?: 'always' | 'design' | 'hover';   // default 'always'; 'design' hides it under static; 'hover' shows it on pointer-over
  actions?: Array<{ id: string; label: string; icon?: string; title?: string; disabled?: boolean }>;
                                          // painted at the end of the band, in order; a press fires onCaptionAction and never selects or drags
  passThrough?: string;                   // presses inside these descendants are content, not the band's
                                          // default 'button, a, input, select, textarea, [data-axdb-pass]'
  className?: string;                     // your class on the band, for per-section theming
  collapsible?: boolean;                  // LATER: a chevron; collapsed sections fold to the band
  collapsed?: boolean;                    // LATER: persisted state
};

Two things deliberately stay out of the kit: what an action does (maximize, export, filters are the app's), and chart-level status. The kit paints the header, reserves its space, routes presses and keeps the theme consistent between widget headers and section headers — that is the boundary it already draws for cards.

Build

  1. Spec and types: caption on DashboardWidgetSpec, renderCaption on DashboardOptions, setCaption/getCaption on the handle; containerWidget metadata carries it; toJSON() and load.ts round-trip it.
  2. Painting: the band is a child of the section's overlay (.axdb-slab), positioned by syncSlabs(); renderCaption paints into it; static and RTL classes as for the grip.
  3. Space: the container binder takes a paddingTop (the band's height plus the gap) so the inner frame starts below the band; the split binder the same; the section-resize floor and the escalation maths include it.
  4. Presses: a press on the band routes to the section-press path added in 0.4.19 (select; edges resize) — through the nested board's forwarding, so registration order never matters.
  5. Gates: unit tests for the option, the reserved space and the round trip; lab scenarios L40–L43 (inside reserves space: the first child's top ≥ the band's bottom at every row height; tab clamps to the gap; a band press selects and a band-edge press resizes; static paints and is inert; RTL mirrors align); the battery, gallery, save/load, interaction, visual and the three variant apps as always; packaging gate last; release as 0.4.22.
  6. Docs and Quantia: the learn page's Containers section; the Quantia prompt gains "replace the .sec tab with caption and delete the overlap".

Defaults, decided

Chosen against what DevExpress, Grafana, Power BI, Superset and Metabase ship, and against the kit's own widget header so a section header and a card header line up.

Next: a tab container

DevExpress ships a Tab Container dashboard item: pages, each holding a group of items, one visible at a time. Power BI has report pages and bookmarks, Grafana has collapsible rows, Tableau has containers; only DevExpress has tabs inside the board, and Quantia replaces DevExpress. It also answers the "VS Code" layout: VS Code's editor area is a split of tab groups. The kit already has split; tabs as a third layout makes a split container whose panes are tab containers, which is that layout.

// a container's layout gains a third mode; nothing else in the spec changes
layout?: 'grid' | 'split' | 'tabs';

{ id: 'analysis', title: 'Analysis', layout: 'tabs', active: 'sales', children: [
    { id: 'sales',   title: 'Sales',   children: [ …widgets… ], layout: 'grid'  },   // page 1
    { id: 'margin',  title: 'Margin',  children: [ …widgets… ], layout: 'split' },   // page 2
    { id: 'notes',   title: 'Notes',   kind: 'text', … },                            // a plain widget becomes a one-widget page
]}

tabs?: {                      // on the container; the strip is the caption band, so the same options apply
  position?: 'top' | 'bottom' | 'start' | 'end';   // default 'top'
  align?: 'start' | 'center' | 'end';              // default 'start'
  stretch?: boolean;          // tabs share the strip width equally — default false
  closable?: boolean;         // × on each tab, fires onTabAction('close') — default false
  reorder?: boolean;          // drag a tab along the strip — default true in design, never under static
};
handle.activateTab(containerId, pageId); handle.getActiveTab(containerId);
onTabChange?(containerId, pageId, viewId);
