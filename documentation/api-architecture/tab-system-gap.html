Tabs: what VS Code does, what the kit does

Every row below was measured against element 0.4.27, not assumed. The verdicts come from driving a real browser: a probe page with eight tabs, a mixed container, a tab container on a split board, tabs nested inside a tab page, a static board, and a widget dragged in and out of an open page.

The model, side by side

VS Code's editor area is a split tree of groups, and each group is a tab bar over one visible editor. The kit has both halves already: layout: 'split' is the tree, layout: 'tabs' is a group. What is missing is almost entirely the drag gestures that move things between them.

Dragging content out: what actually happens

Reported as "the content isn't dropped where I placed it, it goes to the bottom as a new row". Measured, the rule is narrower than that, and worth stating exactly because it is not a tab bug at all.

caseresultverdict

VS Code never relocates a drop. It shows you the zone you are over, and dropping there either joins that group or splits it — the editor cannot "not fit". A grid can, so the kit needs a deliberate answer: refuse the drop visibly the way a full board already does, shrink the tile to the free width, or push the row below down to make room. Quietly landing at the bottom is the one option that surprises people, and it is what happens today.

Two defects the probe found

A non-container child of a tab container is orphaned. The tab system treats only children carrying widgets as pages, so a plain widget among them is never positioned: it paints at the board origin at its 100×60 placeholder size. Measured: 'loose' at x=0, 100×60, while the two real pages tabbed correctly. The same happens when every child is a plain widget: no strip is painted at all and the widget is stranded. The plan always said a plain child should become a one-widget page; the code does not do it yet. Until it does, this is a silent corruption of the author's layout, and it is the first thing to fix.
A one-page container still shows a bar. VS Code destroys a group when its last editor leaves. Combining and tearing out will produce one-page containers constantly, so the collapse rule has to land in the same round as the drag, not after it.

What the drag round actually costs

The three gestures you asked for — move a whole group, move one tab inside a group, pull a tab out into its own group — are one mechanism, not three. Each is a drop with a source and a target zone.

  1. Make a section draggable at all. Today it is a locked slab, which is why moveTo refuses. This is the largest piece and it is not tab-specific: it changes what a section is on the board. Doing it unlocks moving a plain section too, which the kit has never allowed.
  2. A drop-zone overlay over the panel under the pointer: centre and tab bar mean combine, the outer fifth of each side means split. This is the whole VS Code feel, and the split binder already computes edge insertions for widgets, so the geometry is borrowed rather than invented.
  3. Two commands, both undoable in one step: combine converts the target section into a tab container if it is not one and moves the dropped panel in as a page; tear out removes a page, wraps it back into a plain section, and drops it into the board or a new split pane.
  4. Collapse on empty so a container with one page becomes a plain section again, and one with none disappears.
  5. Reorder within the bar, which is the cheap one: a drag along the strip permuting the pages array.
  6. The overflow chevron, so a group with many pages stays usable.

Order matters here. Steps 1 and 4 are prerequisites for the gesture feeling right, and step 1 touches the board's model of a section rather than the tab code. I would ship it as its own round with the section-drag gates rewritten first, then the drop zones on top, rather than bolting the gesture onto locked slabs.

What I checked, and how

Eight tabs in a narrow container for overflow; a container mixing a plain widget with two pages; a container whose children are all plain widgets; a tab container as a pane of a split board; a tab container inside a tab page; a static board; moveTo on both a tab group and a plain section; and a real pointer drag of a widget from the board into the open page and back. Each verdict above cites what it measured. The behaviours marked GAP were confirmed absent, not inferred from the code.
